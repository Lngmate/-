# 多设备实验任务预约

## 使用方式

登录后从“实验任务”进入，填写任务名称、最早开始和最晚完成时间，添加2至3道有序工序。每道工序选择一台设备和30至1440分钟的使用时长；第二道起可以设置与前一道工序的最短间隔。

点击“生成排期方案”查看时间线、等待时间、设备审批方式和预计费用，再确认提交。提交成功后可以在“实验任务”查看进度，在“我的预约”完成各工序的签到、取消与归还，在日历查看设备占用。修改表单会清除旧方案。预览不占用设备；确认时如发生冲突，需要重新生成方案。

冷却期间若仍占用设备，必须计入该设备使用时长；间隔仅代表不占用设备的冷却、转运或准备时间。费用按各设备标准机时价格计算，不自动应用伴热折扣，各工序归还时沿用现有结算逻辑。

## 排程原理

本功能使用确定性约束排程，不调用大语言模型，不需要 API Key。

1. 校验用户课题组、信誉、设备可用状态、工序时长及未来30天内的时间窗口。
2. 读取设备有效预约，按开始时间排序；待导师审批、待管理员审批、已通过及使用中的预约均占用时间。
3. 从最早开始时间寻找第一道工序的空档。遇到冲突，直接跳到冲突预约结束时间，继续检查。
4. 下一道工序的最早时间 = 上一道工序结束时间 + 最短间隔，同样寻找空档。
5. 若任一道工序超出完成期限，返回原因；否则返回整套排期。

对于“设备已选定、工序顺序固定、仅有最短间隔”的模型，尽早结束前一道工序不会减少后一道工序的可选时间，因此逐道寻找最早空档能够获得最早完成的可行方案。算法允许增加间隔等待设备，不支持最大间隔、替代设备选择、工作时间表或多任务全局优化。若单台设备存在m条预约，查询排序约为O(m log m)，扫描为O(m)。

## 一致性与审批边界

确认时按设备ID排序取得互斥锁，与原有单设备预约共用同一组锁，防止同一后端进程内抢占；固定锁顺序避免多设备交叉加锁死锁。同一任务可以再次使用同一设备。事务内重新校验预览给出的精确时段，任务、全部工序预约以及提交通知一起保存；任一步出错全部回滚，不自动挪动用户已确认的时段。

原子性针对提交过程，各工序仍独立审批和履约。一道工序被驳回、取消或爽约时，任务页面会提示处理剩余预约，不会自动取消其他工序。当前不强制检查前置工序实际完成后才允许下一工序签到。多实例部署需增加数据库行锁或分布式锁；目前支持单后端实例。

数据库由GORM启动时自动迁移，新增experiment_tasks表及reservations.task_id、task_step、gap_minutes，不需删除原数据库。

## 接口

均需Bearer Token，任务列表只返回当前用户的数据。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | /api/tasks | 我的任务与各工序预约 |
| POST | /api/tasks/preview | 计算方案，不写预约 |
| POST | /api/tasks | 精确时段确认及整单提交 |

预览请求：

```json
{
  "name": "材料制备与表征",
  "purpose": "比较不同热处理条件下的晶体结构",
  "earliest_start": "2026-10-22T09:00:00+08:00",
  "deadline": "2026-10-24T18:00:00+08:00",
  "steps": [
    {"name": "加热", "equipment_id": 9, "duration_minutes": 120, "gap_minutes": 0},
    {"name": "XRD检测", "equipment_id": 5, "duration_minutes": 30, "gap_minutes": 60}
  ]
}
```

确认请求在相同载荷中加入start_times，内容为预览返回的每道工序start_time，顺序与steps一致。冲突返回HTTP 409。

## 验证与答辩

在backend执行`go test ./...`。测试覆盖空档跳转、间隔、边界相接、审批规则、关联存储、过期方案、事务中途失败回滚、并发重复提交、重复使用同一设备、设备停用及信誉限制。

答辩可先给第二台设备预订一个冲突时段，再生成任务展示自动等待；随后在方案确认前抢占一个工序时段，演示整单拒绝，并核对没有产生部分预约。

如以后加入AI，可让其将自然语言转成工序草案，用户确认设备和参数后继续交给当前排程器校验。实际设备占用与事务提交始终由后端约束控制。
